# PRD：宿舍共好 — 室友公約與噪音管理系統

---

## 1. 專案概述

### 1.1 背景與動機

在大學宿舍或合租公寓中，來自不同背景的室友共同生活，經常因為生活習慣差異而產生摩擦。常見的衝突來源包括：

- **噪音問題**：深夜打遊戲、講電話或放音樂，影響他人休息。
- **公共區域衛生**：碗盤不洗、垃圾不倒、浴室不清理等。
- **費用分攤不清**：電費、水費、共同採買的物資，誰出了多少、誰欠誰錢，算不清楚。
- **口頭約定容易遺忘**：開學初的室友公約，隨時間推移被淡忘，無從追溯。
- **「黑臉」難題**：想提醒室友注意某些行為，但怕傷和氣而選擇隱忍，問題逐漸累積。

目前大多數人依賴 LINE 群組來處理這些事務，但訊息容易被洗掉、無法結構化管理，也缺乏自動化提醒與計算功能。

**本系統旨在提供一個專為共居生活設計的管理平台**，將公約、財務、物資、提醒等功能整合在一個地方，讓室友之間的約定透明化、責任明確化，從根本上減少摩擦與衝突。

### 1.2 目標用戶

| 用戶類型 | 描述 |
| :--- | :--- |
| 大學宿舍學生 | 2～4 人同住一間宿舍，需要管理共同生活事務 |
| 合租族群 | 與他人一起合租的人，需要分攤費用與協調家事 |

### 1.3 核心價值主張

> **「讓系統當黑臉，讓室友做朋友。」**

- **透明化**：所有公約、帳務、排班一目了然，杜絕「我不知道」的藉口。
- **自動化**：系統自動計算電費分攤、定期推送家事提醒，不再需要某個人當「管家」。
- **匿名化**：透過「友善黑臉」功能，以系統名義溫和提醒，避免人際尷尬。
- **歷史化**：所有公約異動與帳務記錄都有跡可循，有爭議時可以回溯查證。

### 1.4 專案目標

| 編號 | 目標 | 對應功能 |
| :---: | :--- | :--- |
| 1 | 不因作息不同吵架 | 友善黑臉、公約異動記錄 |
| 2 | 金錢分配平均 | 共同開支帳本、智慧電費 |
| 3 | 維持生活品質 | 隱形管家、共同物資庫存 |

### 1.5 本次不包含（Out of Scope）

以下項目 **不在** 本次開發範圍內，未來可視需求另行評估：

- **金流交易處理**：系統僅提供帳務記錄與分攤計算，不整合任何線上支付、轉帳或金流服務。
- **實體硬體設備連接**：不連接實體電表、噪音偵測器或 IoT 裝置，所有數據皆由使用者手動輸入。
- **多寢室 / 跨單位管理**：系統僅支援單一租屋群組的管理，不提供跨群組、跨樓層或宿舍管理員的統一管理後台。
- **AI 自動化噪音分析**：不透過麥克風或感測器進行即時噪音偵測與自動判定，噪音提醒僅由室友主動發送。
- **複雜的權限層級系統**：僅區分「群組管理者」與「一般成員」兩種角色，不實作多層級或細粒度的權限控管。

## 2. 功能需求

以下為系統六大核心功能，每項功能均以使用者故事（User Story）格式撰寫，並補充功能細節說明。

---

### 功能 1：智慧電費

> **作為** 合租室友，**我希望** 能輸入每期電費帳單總額與各房間的獨立電表度數，讓系統自動計算並分攤公共用電與個人用電的費用，**以便** 精準且公平地結算每個人應繳的電費，避免電費分攤的爭議。

#### 功能細節

- **帳單登錄**：輸入本期總電費金額、計費期間（起迄日期）。
- **電表度數登錄**：每位室友輸入自己房間的電表起始度數與結束度數。
- **自動計算**：
  - 個人用電度數 = 結束度數 − 起始度數
  - 公共用電度數 = 總度數 − 所有個人度數加總
  - 公共用電費用均攤給所有室友
  - 個人應繳 = 個人用電費用 + 公共分攤費用
- **歷史帳單**：可查閱過去每期的電費分攤紀錄。
- **提醒功能**：帳單登錄後，尚未繳費的室友會收到系統提醒。

---

### 功能 2：隱形管家

> **作為** 忙碌的合租室友，**我希望** 系統能自動定期發出生活庶務的通知（如倒垃圾、繳費截止日、值日生打掃），**以便** 讓「系統」來扮演管家的角色，避免總是由某個人催促大家而感到疲憊或成為眾矢之的。

#### 功能細節

- **排班設定**：管理者可設定循環排班（如每週輪替打掃、倒垃圾）。
- **任務類型**：
  - 週期性任務（每天 / 每週 / 每月）
  - 一次性任務（特定日期的繳費提醒等）
- **通知機制**：任務到期前系統自動發出站內通知。
- **完成確認**：負責人可標記任務為「已完成」，其他室友可查看狀態。
- **輪值日曆**：視覺化顯示每位室友的值班時段。

---

### 功能 3：友善黑臉

> **作為** 怕傷和氣的室友，**我希望** 能透過系統發送匿名的溫和提醒給特定室友（例如「目前音量稍大，能否調小一點？」），**以便** 在不暴露身份、不破壞關係的前提下，反映生活上的困擾。

#### 功能細節

- **匿名提醒**：選擇預設的提醒範本或自訂訊息，以「系統提醒」的名義發送。
- **提醒範本分類**：
  - 噪音類（音量過大、深夜活動等）
  - 衛生類（公共區域清潔、個人物品擺放等）
  - 其他類（冷氣溫度、門窗關閉等）
- **冷卻機制**：同一發送者對同一對象在一定時間內（如 1 小時）只能發送一次，避免惡意騷擾。
- **接收通知**：被提醒者登入後會看到系統提醒訊息，但無法得知發送者身份。
- **統計摘要**：管理者可查看提醒的整體次數與類別統計（不揭露個人），作為公約調整的參考。

---

### 功能 4：共同開支帳本

> **作為** 合租室友，**我希望** 能夠記錄所有共同花費（如購買衛生紙、清潔劑等共用物資），系統能自動計算每人應分攤的金額與目前的應收應付餘額，**以便** 公平且清楚地管理合租財務，結算時不再起爭議。

#### 功能細節

- **記帳功能**：記錄消費項目、金額、付款人、分攤對象（全部或指定成員）。
- **自動分攤**：系統根據設定自動計算每人應付金額。
- **餘額總覽**：清楚顯示每位室友目前的應收 / 應付金額與淨額。
- **結算功能**：支援手動標記「已結清」，重設餘額。
- **帳本歷史**：所有消費紀錄可依日期、類別篩選查閱。

---

### 功能 5：公約異動記錄

> **作為** 合租室友，**我希望** 系統能記錄所有室友公約的制定、修改與刪除歷史，每次異動都能看到「誰」在「什麼時候」改了「什麼內容」，**以便** 所有人隨時查閱最新版本的共識，減少因遺忘或認知不同而產生的爭執。

#### 功能細節

- **公約建立**：以條文形式建立公約內容（如「晚上 11 點後請降低音量」）。
- **版本控制**：每次修改都會保留舊版本，形成完整的變更歷史。
- **異動記錄**：記錄修改人、修改時間、修改前後的差異對比。
- **公約分類**：可依類別分組（噪音管理、衛生清潔、費用分攤、其他約定）。
- **同意機制**：新增或修改公約時，需要所有（或多數）室友確認同意後才生效。

---

### 功能 6：共同物資庫存

> **作為** 合租室友，**我希望** 能夠記錄與查看共同物資（如衛生紙、洗碗精、垃圾袋）的庫存數量，當庫存不足時收到提醒，**以便** 及時補貨，避免突然無物可用的窘境。

#### 功能細節

- **物資清單**：建立共同物資的品項列表，包含名稱、單位、目前數量。
- **入庫 / 出庫登記**：記錄每次採購（入庫）與消耗（出庫）的數量與操作人。
- **低庫存提醒**：為每項物資設定最低庫存量，低於門檻時系統自動通知所有室友。
- **採購建議**：根據消耗速率，推估下次需要補貨的時間。
- **整合帳本**：採購物資時可一鍵將金額同步至「共同開支帳本」。

## 3. 非功能需求

### 3.1 技術限制

| 項目 | 技術選型 |
| :--- | :--- |
| 後端框架 | Flask (Python) |
| 前端模板引擎 | Jinja2 |
| 前端技術 | HTML / CSS / JavaScript（純前端，無框架） |
| 資料庫 | SQLite |
| 版本控制 | Git + GitHub |

### 3.2 效能

- **資料更新效率**：公約修改、帳務記錄、物資庫存等操作送出後，資料應即時寫入資料庫並反映在頁面上，避免使用者需手動重新整理。
- **資訊回應迅速**：頁面載入時間應控制在 **2 秒以內**（一般網路環境下）；電費分攤、帳務計算等運算結果應於提交後 **即時回傳**，不產生明顯等待。
- SQLite 對於小規模群組（2～8 人）的資料量足以負荷，不需額外優化。

### 3.3 安全性

- **密碼安全**：使用者註冊與登入需實作 **密碼雜湊**（如 bcrypt / werkzeug），密碼不得以明文儲存。
- **身份驗證與授權**：系統需實作完整的 **登入 / 登出機制**，所有需授權的頁面皆須驗證使用者身份；不同角色（管理者 / 一般成員）應有對應的 **權限控管**。
- **資料保密與隔離**：群組資料需進行嚴格的 **權限隔離**，非群組成員不可存取該群組的任何資料（公約、帳務、物資等）。
- 所有表單需加入 **CSRF Token** 防護。
- 使用 **參數化查詢** 防止 SQL Injection。

### 3.4 易用性

- **直覺化操作**：操作流程應 **簡潔直覺**，目標用戶為非技術背景的大學生，首次使用即能快速上手，不需額外教學。
- **錯誤回饋**：當使用者輸入不合法資料或操作失敗時，系統應提供 **清楚且友善的錯誤訊息**，引導使用者修正；重要操作（如刪除公約、結算帳務）需有 **二次確認** 機制，防止誤操作。
- **響應式網頁設計（RWD）**：介面需採響應式設計，確保在 **桌機、平板與手機** 上皆有良好的瀏覽與操作體驗，符合大學生與年輕族群以手機為主的使用習慣。
